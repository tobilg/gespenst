Ghostty VT for the web

A real Ghostty terminal, running in the browser.

Gespenst drives the official Ghostty VT engine from TypeScript: unmodified WASM parsing, worker isolation, byte-native streams, and much more.

Checking browser runtime

A browser-only Bash session with a virtual filesystem, running in this tab with no backend, PTY server, or cross-origin isolation requirement.

Official Ghostty core The unmodified nightly ghostty-vt.wasm, checksummed and ABI-verified before a terminal is created.
Off the main thread Parsing and rendering run in a dedicated worker by default, with shared-worker and main-thread fallbacks.
Bytes end to end PTY output stays Uint8Array from the socket to Ghostty. Nothing is decoded to strings on the way.
Shells without a server Browser shell runtimes run in the page, so a working shell needs no PTY host or backend deployment.

Start with the native API.

Keep PTY bytes intact from the socket to Ghostty. Framework adapters wrap the same terminal, and compatibility is added only where an existing integration needs it.

Know what runs where.

Gespenst separates process transport, VT state, and rendering. Choose each boundary independently without translating terminal output or adopting a prescribed backend.

Pick execution by terminal count.

The default selects a dedicated worker when the browser supports it and falls back safely.

'dedicated'Recommended
One isolated worker per terminal. Use this for most applications and single-session views.
'shared'Many sessions
Multiplex terminals through one worker when worker count matters. Busy sessions share its event loop.
falseMain thread
Useful for tests, constrained embeds, and unsupported environments. Parsing competes with application work.

The integration contract

Terminals are a security boundary. Gespenst draws the line in one place so escape sequences never turn into browser actions on their own.

Gespenst owns

VT parsing, terminal state, input encoding, and rendering.

Your application owns

Process lifecycle, authentication, authorization, transport policy, and clipboard permission.

One core, composable parts.

Every package ships as ESM with lockstep versions, so nothing you skip ends up in the bundle. Each entry links to its generated API reference.

Core

  • @gespenst/core Browser terminal, renderers, addon host
  • @gespenst/core/headless Ghostty VT state machine without a DOM
  • @gespenst/themes Curated, tree-shakable light and dark themes

Processes

  • @gespenst/websocket Binary transport, resize protocol, reconnect
  • @gespenst/shell Stable portable Bash facade powered by BashKit
  • @gespenst/bashkit Single-process Bash without browser isolation
  • @gespenst/xterm xterm.js 6.0 stable public API compatibility

Addons

  • @gespenst/clipboard Permission-aware text and MIME paste
  • @gespenst/search Buffer search with viewport highlights
  • @gespenst/web-links Safe HTTP(S) detection and activation
  • @gespenst/web-fonts Document and worker web-font loading
  • @gespenst/serialize Versioned snapshots with build metadata

Frameworks

  • @gespenst/react Component and hook
  • @gespenst/vue Component and composable
  • @gespenst/svelte Action with runtime font and theme updates

Guides for the whole path.

The core guide walks from first render to production concerns: transports, configuration, fonts, permissions, performance, and the failure modes worth knowing early.

Getting Started Create a responsive terminal with default worker and renderer selection. Connecting a PTY Wire input and output without imposing a server protocol on the core. Configuration Choose settings by host application, terminal count, and accessibility. Layout, Fonts, and Themes Keep cells aligned by making layout and font loading explicit. Theming Flat, xterm-compatible theme values normalized outside the render loop. Events, Permissions, and Lifecycle Treat escape-sequence effects as requests, not automatic browser actions. Performance Preserve the byte-native path, then measure under representative output. Headless Runtime Parsing, input encoding, events, and snapshots without a DOM. Migrating from xterm.js Adopt the native API, or keep a compatibility boundary while you move. Troubleshooting Start at the first visible symptom, then verify each boundary in turn.
